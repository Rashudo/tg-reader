# tg-reader

Читает новые сообщения публичного Telegram-канала **от имени вашего аккаунта**
(подписки достаточно, админка не нужна), сверяет их с массивом ключевых слов
и пересылает совпадения вам в Избранное.

## Как это работает

Обычный бот (Bot API) не видит сообщения в чужом канале — его туда нужно добавить
администратором. Поэтому здесь используется MTProto-клиент (GramJS): он логинится
вашим аккаунтом и видит ровно то же, что видите вы в приложении.

## Установка

```bash
npm install
```

## Настройка

1. Получите `api_id` и `api_hash` на https://my.telegram.org → **API development tools**
   (заявка на приложение, название любое).

2. Заполните `.env`:

   ```
   TG_API_ID=1234567
   TG_API_HASH=abcdef...
   CHANNEL=@durov            # канал-источник; можно несколько через запятую
   TARGET=me                 # me = Избранное; либо @username или id чата
   ```

3. Войдите в аккаунт — один раз:

   ```bash
   npm run login
   ```

   Спросит телефон, код из Telegram и пароль 2FA (если включён), затем сам запишет
   строку сессии в `TG_SESSION`. Больше вводить код не потребуется.

4. Задайте ключевые слова в `keywords.js`. Они разбиты на группы, регистр не
   учитывается, «ё» = «е». Ключ бывает двух видов:

   ```js
   module.exports = [
     {
       group: 'Телевизоры',
       words: [
         'телевизор',    // подстрока: поймает «телевизоры», «телевизором»
         { word: 'тв' }, // отдельное слово: поймает «ТВ-приставка», «смарт тв»,
                         // но не «ответ», «твой», «творог»
       ],
     },
   ];
   ```

   Короткие ключи в 2-3 буквы почти всегда стоит писать через `{ word: ... }` —
   как подстрока они цепляют половину словаря. Длинные удобнее подстрокой: так
   ловятся все падежи и множественное число разом.

   Чтобы временно снять целую группу, не трогая слов, впишите её имя в
   `DISABLED_GROUPS` в `.env`:

   ```
   DISABLED_GROUPS=Клавишные
   ```

   Несколько групп — через запятую, регистр не важен. Новая группа в
   `keywords.js` работает сразу, включать её нигде не нужно. Переключатель
   держится в `.env`, а не в `keywords.js`, чтобы выключенная группа не висела
   вечным локальным изменением в git.

## Запуск

```bash
npm start
```

В консоль пишется строка на каждое совпадение с именем сработавшей группы. Ctrl+C — остановка.

Позиция чтения и список уже отправленных сообщений по каждому каналу хранятся в
`state.json`, поэтому посты, вышедшие
за время простоя (рестарт, обрыв связи, правка `keywords.js`), после запуска
догружаются и проверяются. На **первом** запуске бот ничего не пересылает — только
запоминает точку отсчёта, чтобы не завалить Избранное старыми объявлениями. Если
нужно проверить архив, для этого есть `npm run scan`.

## Проверить ключевые слова, не дожидаясь новых постов

```bash
npm run scan           # прогнать последние 100 сообщений канала
npm run scan -- 500    # последние 500
```

Ничего не пересылает и не двигает позицию чтения — просто показывает, что бы сработало.

## Тесты

```bash
npm test
```

Покрыт матчер (границы слова, `ё`=`е`, спецсимволы в ключах, ложные срабатывания
из реального прогона), нормализация id чатов, обрезка длинного текста и хранение
позиции чтения.

## Ежедневная сводка новостного канала

Отдельная от пересылки объявлений задача: читать новостной канал целиком, отбрасывать
шум и раз в сутки присылать сгруппированную выжимку. Отбором и группировкой занимается
Claude — ключевыми словами такое не решается.

Настройка в `.env`:

```
ANTHROPIC_API_KEY=sk-ant-...
NEWS_CHANNELS=@some_news_channel
NEWS_HOUR=7                      # час по NEWS_TZ, не по UTC
```

Без `ANTHROPIC_API_KEY` или без `NEWS_CHANNELS` сводка просто выключена, остальное
работает как раньше — в лог при старте пишется, чего не хватает.

Верно и обратное: можно оставить только сводку, убрав `CHANNEL` или выключив все группы
слов. Пересылка объявлений тогда не запускается, а сервис работает. Внешняя проверка про
этот режим знает и не считает застоем отсутствие пересылок.

Сводку собирает **сам работающий сервис**, а не отдельный скрипт по cron. Это не
украшение: второй процесс с той же строкой сессии лишает работающий экземпляр потока
апдейтов, и он молча перестаёт видеть сообщения.

### Что приходит

Сообщения за сутки уходят в модель одним запросом. Она отбрасывает рекламу, призывы
подписаться, анонсы, опросы и повторы одной новости, а остальное группирует по темам,
которые выделяет сама. В сводке видно, сколько сообщений просмотрено и сколько
отброшено.

```
Сводка «Топор Live» за 3 сентября
Просмотрено сообщений: 108, отброшено как шум: 68

▪ Россия: атаки дронов и оборона
   • ПВО сбила 426 БПЛА над регионами РФ в течение дня.
   • С начала суток на подлете к Москве сбили 116 дронов, аэропорты ограничили работу.
```

Длину задаёт `NEWS_MAX_ITEMS` (по умолчанию 35 пунктов). Потолок соблюдается в коде,
а не только просьбой в промпте: модель регулярно выдаёт больше, и лишнее отрезается
с конца. Поэтому в промпте отдельно требуется ставить важное первым — иначе обрезка
резала бы вслепую.

Ссылки на оригиналы выключены (`NEWS_LINKS=off`): у приватного канала они открываются
только у того, кто сам на него подписан, а сводку может читать другой аккаунт.
Включаются одной переменной.

### Сколько стоит

Замерено на живом канале: 108 сообщений с текстом за сутки — 16 тысяч токенов на
входе, около 5 тысяч на выходе при 35 пунктах. Это `claude-haiku-4-5` за $0,041 в
день, то есть **около $1,25 в месяц**. На `claude-opus-5` тот же объём стоил бы
примерно $6,3 в месяц. Модель меняется переменной `NEWS_MODEL`.
Стоимость каждого прогона пишется в журнал:

```
Сводка: claude-haiku-4-5, токенов на входе 16354, на выходе 4996, примерно $0.0413
```

Потолок `NEWS_MAX_MESSAGES` (по умолчанию 400) ограничивает счёт, если в канале
случится всплеск.

### Проверить руками

```bash
# подогнать промпт без Telegram и без остановки сервиса
npm run digest -- --from-file messages.json

# полный путь без отправки (сервис остановить — одна сессия за раз)
systemctl stop tg-reader
npm run digest -- --dry-run
systemctl start tg-reader
```

Без `--dry-run` сводка уйдёт получателю. Запуск руками не смотрит на расписание —
собирает сразу.

### Ровно один запрос к каналу в сутки

Канал опрашивается строго один раз за сутки, независимо от того, чем кончился прогон.
Отметка о суточной попытке ставится **до** запроса, а не после успешной отправки:
иначе сбой модели или пустой канал заставляли бы таймер лезть в Telegram каждые
10 минут до конца дня — в моделировании суток это 102 запроса вместо одного.

Позиция чтения при этом двигается только после успешной отправки, так что новости не
теряются: следующая сводка возьмёт период пошире. В журнал идёт запись, в бота —
тревога.

«Раз в сутки» считается по календарным суткам в зоне `NEWS_TZ`, а не по числу часов
между прогонами: иначе вечерний ручной запуск отменил бы утреннюю сводку следующего
дня, а перестановка часа посреди дня дала бы второй опрос.

Пробный прогон (`--dry-run`) суточную попытку не расходует.

## Уведомления о проблемах

Сервис может молчать по трём причинам: совпадений нет, он упал, или он жив, но
перестал получать сообщения. Со стороны это неразличимо, поэтому о проблемах
сообщает отдельный бот.

Настройка один раз:

1. Создайте бота у [@BotFather](https://t.me/BotFather), положите токен в `.env`:

   ```
   ALERT_BOT_TOKEN=123456:AA...
   ```

2. Напишите своему боту `/start` (иначе он не имеет права вам писать).

3. Заберите `chat_id` автоматически:

   ```bash
   npm run alert-setup
   ```

   Скрипт запишет `ALERT_CHAT_ID` в `.env` и пришлёт проверочное сообщение.

4. Поставьте внешнюю проверку в cron — она узнаёт то, о чём упавший процесс
   сообщить уже не может:

   ```
   */5 * * * * /usr/bin/node /путь/к/tg-reader/src/healthcheck.js >> /var/log/tg-reader-health.log 2>&1
   ```

Без `ALERT_BOT_TOKEN` всё работает как раньше, тревоги идут только в журнал.

### О чём придёт сообщение

| Событие | Кто замечает | Что делает сервис |
|---|---|---|
| Сервис не запущен | cron-проверка | — |
| Перезапускается по кругу (3 раза подряд) | cron-проверка | — |
| Нет сообщений из канала 30 минут | сам сервис | принудительно переподключается и догружает пропущенное |
| Не помогло, тишина 45 минут | сам сервис | выходит с кодом 1, systemd поднимает заново |
| Нет связи с Telegram 5 минут | сам сервис | выходит с кодом 1 |
| Совпадение не удалось переслать | сам сервис | пишет `ПОТЕРЯНО` и шлёт ссылку на оригинал |

Сообщения приходят **только о проблемах**. Ни «снова в норме», ни отчёта
«сутки без происшествий» по умолчанию нет: раз в сутки отчёт включается
переменной `DIGEST_HOUR` (без неё — выключен). Плата за тишину в том, что
молчание бота больше не отличить от сломанной cron-проверки; проверить её
можно руками — `npm run health -- --verbose`.

Одна и та же тревога не повторяется чаще раза в час, но после того как
проблема прошла, следующая приходит сразу, а не через час.

Ночная тишина в канале за проблему не считается. Сервис, когда сам не видит
сообщений дольше получаса, спрашивает у Telegram, есть ли в канале что-то
новое; если нет — записывает момент проверки в `state.json`, и внешняя
проверка считает это признаком жизни наравне с пересланным сообщением.

Пороги настраиваются в `.env`, см. `.env.example`.

## Автоответы в чате

Третья задача сервиса: в чате, указанном в `REPLY_CHAT` (идентификатор
«меченый»: у обычной группы это минус и число, у супергруппы — `-100…`),
аккаунт отвечает сам —
модель пишет реплику, она уходит **от вашего имени, без подтверждения**.

Два контура работают независимо.

**Обращения.** Сообщение считается обращённым к вам, если это ответ на вашу
реплику или в нём есть ваше имя из `REPLY_ALIASES`. Ответ не уходит сразу:
он ждёт две-четыре минуты, и если вы за это время ответили сами, заготовка
снимается. Что считать «ответили сами», задаёт `REPLY_OWNER_CANCEL`: `answer` —
вы ответили на сам вопрос или сказали что-то в первую минуту после него,
`any` — вы вообще написали в чат хоть что-нибудь. На живых сутках разница
оказалась семикратной: `any` оставил один ответ, `answer` — шесть.

Заготовка, упёршаяся в паузу или бюджет, не выбрасывается: она остаётся в
очереди и проверяется снова каждые 30 секунд, пока не устареет.

**Своя воля.** Раз в 25 минут сервис смотрит на накопившееся окно и спрашивает
модель, есть ли повод вставить одну фразу. Молчит, если бюджет исчерпан, идут
тихие часы, вы говорили сами последние 15 минут или новых сообщений меньше
пяти.

### Потолки

| Что | По умолчанию | Переменная |
|---|---|---|
| Реплик по своей воле в сутки | 4 | `REPLY_DAILY_BUDGET` |
| Пауза между ними | 90 мин | `REPLY_SPONTANEOUS_PAUSE_MIN`, короче — `REPLY_SPONTANEOUS_PAUSE_SEC` |
| Ответов на обращения в сутки | 10 | `REPLY_ADDRESSED_BUDGET` |
| Пауза между ними | 5 мин | `REPLY_ADDRESSED_PAUSE_MIN`, короче — `REPLY_ADDRESSED_PAUSE_SEC` |
| Задержка перед отправкой | 2–4 мин | `REPLY_DELAY_MIN_SEC` / `REPLY_DELAY_MAX_SEC` |
| Тихие часы | 23:00–09:00 | `REPLY_QUIET_FROM` / `REPLY_QUIET_TO` |
| Длина реплики | 160 символов | `REPLY_MAX_CHARS` |
| Заготовка ждёт своей очереди | 10 мин | `REPLY_STALE_AFTER_MIN` |

### Как выключить

Три способа, любой действует немедленно и переживает перезапуск:

- кнопка «Больше не отвечать» под копией каждого отправленного ответа;
- сообщение боту: `стоп`, обратно — `старт`, состояние — `статус`;
- `REPLY_ENABLED=off` в `.env` и перезапуск.

Одна и та же шутка дважды не уходит: перед отправкой реплика сверяется с шестью
предыдущими, и совпадение по двум значащим словам подряд считается повтором.
Это лечит петлю, в которую бот попадает, когда чат подхватывает его же фразу.

Копия каждого ответа приходит вам в бота сразу после отправки — чтобы вы
увидели её раньше собеседников.

### Голос

Реплики пишутся по образцам вашей собственной речи из этого же чата. Собрать:

```bash
systemctl stop tg-reader && npm run voice && systemctl start tg-reader
```

Скрипт кладёт `voice.json` рядом с `.env` (в git не попадает). Без него ответы
будут безликими — сервис об этом предупредит в журнале.

### Проверить, не включая

```bash
npm run replies -- --from-file выгрузка.json
```

Прогоняет оба контура по сохранённым суткам чата, ничего не отправляет и
печатает, где бы бот заговорил, что бы сказал и почему промолчал в остальных
случаях. Один такой прогон на 438 сообщениях стоил около четырёх центов.

### Что уходит в Anthropic

Окно из 30 последних сообщений чата и ваши образцы речи — то есть переписка
ваших собеседников, а не только ваша.

### Проверить состояние руками

```bash
npm run health -- --verbose      # что видит cron-проверка прямо сейчас
systemctl show tg-reader -p NRestarts
stat -c '%y' state.json          # когда сервис последний раз видел сообщение
```

Внешняя проверка **не ходит в Telegram** — читает только `systemctl` и
`state.json`. Это важно: второй MTProto-клиент на той же сессии молча лишает
работающий сервис потока апдейтов. По той же причине не запускайте `npm run scan`
и вторую копию сервиса, пока сервис работает.

## Круглосуточная работа (systemd)

```bash
cp tg-reader.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now tg-reader
journalctl -u tg-reader -f
```

## Важное

- `.env` содержит строку сессии — это фактически доступ к вашему аккаунту.
  Файл в `.gitignore`, права на него выставляются в `600`. Не публикуйте и не передавайте.
- Если в канале включён запрет на пересылку, бот пришлёт копию текста со ссылкой
  на оригинал вместо форварда. Копия отправляется без разметки, ровно как в оригинале.
- Ключевые слова ищутся в тексте сообщения и в подписи к медиа. Текст на картинках
  (без подписи) не распознаётся.
- Альбом (несколько фото одним постом) пересылается целиком, а не одной картинкой.
- Отредактированный пост проверяется заново: если ключевое слово добавили правкой,
  объявление всё равно придёт.
- Если сообщение совпало, но отправить его не удалось, в лог пишется строка
  `ПОТЕРЯНО …` со ссылкой на оригинал — молча такие случаи не проглатываются.
  В пределах запущенного процесса повтор апдейта от Telegram приведёт к новой
  попытке, но после перезапуска такое сообщение заново не проверяется: ссылка
  из лога — единственный способ его не потерять.
- При потере связи с Telegram дольше 5 минут процесс завершается с ненулевым кодом,
  чтобы systemd поднял его заново; пропущенное за это время догрузится.
- Молчание канала само по себе застоем не считается. Прежде чем объявить застой,
  сервис спрашивает у Telegram, есть ли в канале что-то новее прочитанного: ночью
  барахолка молчит часами, и без этой проверки сервис перезапускался бы всю ночь.
- Правки в `keywords.js` подхватываются при перезапуске.
- Не запускайте вторую копию сервиса и `npm run scan` при работающем сервисе:
  оба используют одну строку сессии, и Telegram перестаёт слать апдейты рабочей
  копии. Признак — `state.json` перестал обновляться.
