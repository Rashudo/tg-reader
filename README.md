# tg-reader

Читает новые сообщения публичного Telegram-канала **от имени вашего аккаунта**
(подписки достаточно, админка не нужна), сверяет их с массивом ключевых слов
и пересылает совпадения вам в Избранное.

## Как это работает

Обычный бот (Bot API) не видит сообщения в чужом канале — его туда нужно добавить
администратором. Поэтому здесь используется MTProto-клиент (GramJS): он логинится
вашим аккаунтом и видит ровно то же, что видите вы в приложении.

## Установка

```bash
npm install
```

## Настройка

1. Получите `api_id` и `api_hash` на https://my.telegram.org → **API development tools**
   (заявка на приложение, название любое).

2. Заполните `.env`:

   ```
   TG_API_ID=1234567
   TG_API_HASH=abcdef...
   CHANNEL=@durov            # канал-источник; можно несколько через запятую
   TARGET=me                 # me = Избранное; либо @username или id чата
   ```

3. Войдите в аккаунт — один раз:

   ```bash
   npm run login
   ```

   Спросит телефон, код из Telegram и пароль 2FA (если включён), затем сам запишет
   строку сессии в `TG_SESSION`. Больше вводить код не потребуется.

4. Задайте ключевые слова в `keywords.js`. Регистр не учитывается, «ё» = «е».
   Ключ бывает двух видов:

   ```js
   module.exports = [
     'телевизор',    // подстрока: поймает «телевизоры», «телевизором»
     { word: 'тв' }, // отдельное слово: поймает «ТВ-приставка», «смарт тв»,
                     // но не «ответ», «твой», «творог»
   ];
   ```

   Короткие ключи в 2-3 буквы почти всегда стоит писать через `{ word: ... }` —
   как подстрока они цепляют половину словаря. Длинные удобнее подстрокой: так
   ловятся все падежи и множественное число разом.

## Запуск

```bash
npm start
```

В консоль пишется строка на каждое совпадение. Ctrl+C — остановка.

Позиция чтения и список уже отправленных сообщений по каждому каналу хранятся в
`state.json`, поэтому посты, вышедшие
за время простоя (рестарт, обрыв связи, правка `keywords.js`), после запуска
догружаются и проверяются. На **первом** запуске бот ничего не пересылает — только
запоминает точку отсчёта, чтобы не завалить Избранное старыми объявлениями. Если
нужно проверить архив, для этого есть `npm run scan`.

## Проверить ключевые слова, не дожидаясь новых постов

```bash
npm run scan           # прогнать последние 100 сообщений канала
npm run scan -- 500    # последние 500
```

Ничего не пересылает и не двигает позицию чтения — просто показывает, что бы сработало.

## Тесты

```bash
npm test
```

Покрыт матчер (границы слова, `ё`=`е`, спецсимволы в ключах, ложные срабатывания
из реального прогона), нормализация id чатов, обрезка длинного текста и хранение
позиции чтения.

## Уведомления о проблемах

Сервис может молчать по трём причинам: совпадений нет, он упал, или он жив, но
перестал получать сообщения. Со стороны это неразличимо, поэтому о проблемах
сообщает отдельный бот.

Настройка один раз:

1. Создайте бота у [@BotFather](https://t.me/BotFather), положите токен в `.env`:

   ```
   ALERT_BOT_TOKEN=123456:AA...
   ```

2. Напишите своему боту `/start` (иначе он не имеет права вам писать).

3. Заберите `chat_id` автоматически:

   ```bash
   npm run alert-setup
   ```

   Скрипт запишет `ALERT_CHAT_ID` в `.env` и пришлёт проверочное сообщение.

4. Поставьте внешнюю проверку в cron — она узнаёт то, о чём упавший процесс
   сообщить уже не может:

   ```
   */5 * * * * /usr/bin/node /путь/к/tg-reader/src/healthcheck.js >> /var/log/tg-reader-health.log 2>&1
   ```

Без `ALERT_BOT_TOKEN` всё работает как раньше, тревоги идут только в журнал.

### О чём придёт сообщение

| Событие | Кто замечает | Что делает сервис |
|---|---|---|
| Сервис не запущен | cron-проверка | — |
| Перезапускается по кругу (3 раза подряд) | cron-проверка | — |
| Нет сообщений из канала 30 минут | сам сервис | принудительно переподключается и догружает пропущенное |
| Не помогло, тишина 45 минут | сам сервис | выходит с кодом 1, systemd поднимает заново |
| Нет связи с Telegram 5 минут | сам сервис | выходит с кодом 1 |
| Совпадение не удалось переслать | сам сервис | пишет `ПОТЕРЯНО` и шлёт ссылку на оригинал |
| Всё в порядке | cron-проверка | суточная сводка в 09:00 |

Одна и та же тревога не повторяется чаще раза в час; когда всё налаживается,
приходит отдельное «снова в норме». Суточная сводка нужна и затем, чтобы
доказать, что сам канал уведомлений жив — тишина перестаёт быть двусмысленной.

Пороги настраиваются в `.env`, см. `.env.example`.

### Проверить состояние руками

```bash
npm run health -- --verbose      # что видит cron-проверка прямо сейчас
systemctl show tg-reader -p NRestarts
stat -c '%y' state.json          # когда сервис последний раз видел сообщение
```

Внешняя проверка **не ходит в Telegram** — читает только `systemctl` и
`state.json`. Это важно: второй MTProto-клиент на той же сессии молча лишает
работающий сервис потока апдейтов. По той же причине не запускайте `npm run scan`
и вторую копию сервиса, пока сервис работает.

## Круглосуточная работа (systemd)

```bash
cp tg-reader.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now tg-reader
journalctl -u tg-reader -f
```

## Важное

- `.env` содержит строку сессии — это фактически доступ к вашему аккаунту.
  Файл в `.gitignore`, права на него выставляются в `600`. Не публикуйте и не передавайте.
- Если в канале включён запрет на пересылку, бот пришлёт копию текста со ссылкой
  на оригинал вместо форварда. Копия отправляется без разметки, ровно как в оригинале.
- Ключевые слова ищутся в тексте сообщения и в подписи к медиа. Текст на картинках
  (без подписи) не распознаётся.
- Альбом (несколько фото одним постом) пересылается целиком, а не одной картинкой.
- Отредактированный пост проверяется заново: если ключевое слово добавили правкой,
  объявление всё равно придёт.
- Если сообщение совпало, но отправить его не удалось, в лог пишется строка
  `ПОТЕРЯНО …` со ссылкой на оригинал — молча такие случаи не проглатываются.
  В пределах запущенного процесса повтор апдейта от Telegram приведёт к новой
  попытке, но после перезапуска такое сообщение заново не проверяется: ссылка
  из лога — единственный способ его не потерять.
- При потере связи с Telegram дольше 5 минут процесс завершается с ненулевым кодом,
  чтобы systemd поднял его заново; пропущенное за это время догрузится.
- Правки в `keywords.js` подхватываются при перезапуске.
- Не запускайте вторую копию сервиса и `npm run scan` при работающем сервисе:
  оба используют одну строку сессии, и Telegram перестаёт слать апдейты рабочей
  копии. Признак — `state.json` перестал обновляться.
